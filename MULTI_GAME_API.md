# Multi-game API data — proposal

How the library, the site and the extension come to serve more than one game's engine API.

Status: **implemented, except the acquisition of new games' data.** All five games are served,
browsable, honestly labelled, and reachable from the extension. Phases 1–3 landed and phase 0 was
solved at the endpoint rather than in the generator (see [What shipped](#7-what-shipped)); phase 4
is still open. Numbers are measured from the tree at `b89be00` unless stated otherwise.

---

## 1. Where the three halves actually stand

The three parts of the project are at three different stages, and only one of them is behind.

**The server is already multi-game and finished.** `GameProfile.DataFilePrefix` selects every
bundled artifact by name, `ApiLoader`/`ObjectFields`/`StockScripts` take a profile, and five games
ship a full data set:

| prefix | api_gsc | api_csc | object_fields | radiant_keys | stock scripts |
|---|--:|--:|--:|--:|--:|
| `cod4` | 819 | — | 108 (entity only) | 297 | 894 |
| `waw` | 1,060 | 188 | 105 (entity only) | 360 | 1,977 |
| `mw2` | 1,111 | — | 108 (entity only) | 367 | 1,488 |
| `bo1` | 1,377 | 320 | 108 (entity only) | 466 | 3,125 |
| `t7` | 2,191 | 803 | 10 kinds, 635 fields | 350 | 980 |

So the premise that CoD4 and WaW "are available and need transforming" is a release behind: all
four pre-BO3 libraries were generated, corrected, recased and shipped. The work left is not
acquiring their data — it is that **nothing outside the language server can see it**.

**The site is BO3-only, in three hardcoded places.**

- `site/src/routes/api/getLibrary/+server.ts` — statically imports `t7_api_{gsc,csc}.json` and
  400s on any other `gameId`.
- `site/src/routes/(gscode)/library/[languageId]/+layout.ts:8` — `const gameId = "t7";`
- `site/src/lib/components/app/pages/editor/EditorSidebar.svelte:188` — `?gameId=t7&…`

Everything underneath is already game-parameterised: `ScrLibrary` carries `gameId`, `ApiLibrarian`
takes and re-derives on it, `getLibrary(fetch, gameId, languageId)` passes it through. The concept
is plumbed; only the call sites are pinned.

**The extension selects a game correctly and then forgets it.** `gscode.game` reaches the server as
`--game` before the DI container is built, the status bar reflects the server's answer, and
`gscode/gameMismatch` offers to switch. But `client/src/extension.ts:93,108` builds
`https://www.gscode.net/library/{gsc|csc}[/{name}]` with no game in the path — so shift+F1 on a
CoD4 script opens BO3's page for that name, or a 404.

## 2. Four measured blockers

These are not design questions; they are current facts that would break on day one.

### 2.1 Only the BO3 files carry an envelope

`t7_api_gsc.json` and `t7_api_csc.json` are `{ gameId, languageId, revision, revisedOn, api[] }`.
The four pre-BO3 files are bare `{ api[] }`.

`ScrLibrarySchema` requires all four envelope fields (`revisedOn` non-optional, transformed to a
`Date`). Pointing the site at `cod4_api_gsc.json` today throws inside `parseAsync` — in the library
loader *and* in the editor's file import. This is a two-line change in the field-data writer, but
it has to come first.

### 2.2 The flag vocabulary has forked

| file | flags present |
|---|---|
| `t7_api_gsc` | `processed` 2032, `verified` 157, `unlisted` 3, `corrected` 1, `Broken` 1 |
| `cod4_api_gsc` | `documented` 791, `corrected` 47, `aiGenerated` 20 |
| `waw_api_gsc` | `documented` 773, `aiGenerated` 93, `processed` 70, `corrected` 47, `verified` 6 |
| `bo1_api_gsc` | `documented` 762, `processed` 321, `aiGenerated` 259, `corrected` 47, `verified` 27 |
| `mw2_api_gsc` | `documented` 791, `aiGenerated` 264, `processed` 47, `corrected` 47, `verified` 1 |

The site knows a different set: `autogenerated | processed | verified | unlisted`
(`FlagEditor.svelte`, `validation.ts:38`, `function-editor.svelte.ts:126`). It has never heard of
`documented`, `aiGenerated` or `corrected`.

Two consequences, both silent:

- The editor's stats bucket everything that is neither `verified` nor `processed` into
  `autogeneratedCount` — so CoD4's 791 **documented** functions would present as autogenerated.
- `createFunction` stamps `flags: ['autogenerated']`, a flag no generator emits and nothing reads.

The generator's vocabulary is the one carrying evidence (`documented` means a real page,
`aiGenerated` means reconstructed from call sites, `corrected` means an override applied). Teach the
site that set; do not push the site's set back into the data.

### 2.3 The editor silently drops fields on round-trip

The pre-BO3 entries carry two fields BO3's do not: `module` (CoD4 has 38 categories — Math, AI,
Player, Vehicles, HUD…) and `spmp` (`SP` 367, `MP` 85 on CoD4). Neither is in
`ScrFunctionSchema`, and `z.object` strips unknown keys at parse — so loading a CoD4 library into
the editor and exporting it deletes both, with no warning. `remarks` survives (it is in the schema);
`confidence` survives.

Separately, the **server's** `ApiLoader` binds only `name/description/overloads/example/devOnly` —
`flags`, `confidence`, `remarks`, `module`, `spmp` never reach the runtime at all. That is fine for
hover today, but it means the trust story lives only in the JSON and in C# flags, never in the same
place.

### 2.4 The site and server hold separate copies

`site/README.md` states it: the two `t7_api_*.json` are "copies, not a shared source". They are in
**one repo**. Both are at `revision 32`, but the files already differ. This is a drift class that
does not need to exist, and multiplying it by five games makes it five times worse.

### 2.5 (Related) trust metadata is not in the data

`HasCompleteBuiltinLibrary`, `HasReliableBuiltinSignatures` and `HasTrustedEngineNames` are C#
fields on `GameProfile`. The site has no way to know that WaW's signatures are CoD4's inherited
guesses, or that 264 of MW2's entries were reconstructed from call sites. Rendering those as plain
documentation would be exactly the "confident lie" `BuiltinApiSet.EngineNamesFor` was typed to
prevent — the same mistake, one layer out.

## 3. Proposal

Five phases. Phases 0–3 ship real value using only data that already exists. Phase 4 is the part
that needs new sources.

### Phase 0 — make the artifacts uniform

In `tools/field-data`, one pass over the writers:

1. **Emit the envelope for every game.** `{ gameId, languageId, revision, revisedOn, api[] }` on all
   eight files. `revision` starts at 1 for the four that have none.
2. **Add a `provenance` block** to the envelope, so a consumer need not read C#:

   ```json
   "provenance": {
     "complete": false,
     "reliableSignatures": false,
     "primarySource": "wordfile",
     "inheritsFrom": "cod4"
   }
   ```

   Generated from the profile plus what the run already prints
   (`819 (792 documented, 19 reconstructed, 0 inherited, 8 name-only, 6 corrected)`).
3. **Settle the flag vocabulary** on the generator's set and document it in `FOLDER.md`.

Cost, stated plainly: every generated file is hashed into `ServerBuildIdentity`, so this invalidates
every workspace cache on every machine. That is correct behaviour and the reason to do it **once,
in one commit**, rather than a file at a time.

### Phase 1 — one source of truth for the artifacts

Delete the copy. Add a `site` prebuild step that copies
`server/src/GSCode.Workspace/Api/*_api_*.json` into `site/src/lib/apiSource/`, and gitignore the
destination. The "copies, not a shared source" note is a leftover from when the two lived in
different repos; they no longer do.

If copying at build time is unwanted, the fallback is a CI check asserting the files are
byte-identical — but that only reports drift, where copying prevents it.

### Phase 2 — the site becomes multi-game

**Routes.** `/library/[game]/[languageId]/[[func]]`, with:

- `/library` → `/library/bo3/gsc`
- `/library/gsc`, `/library/csc`, `/library/gsc/<name>` → **301** to the `bo3` equivalent.

The redirect is what keeps every existing shift+F1 link, wiki link and bookmark alive, so the
extension's URL contract can change without a flag day.

Use the profile's `ShortName` (`bo3`) in the URL rather than the `Id` (`t7`) — it is what
`gscode.game` already spells, what the README table uses, and what a user would type. The payload's
`gameId` stays `t7`; the route maps one to the other.

**`/api/getLibrary`.** Serve any prefix that has a file; 400 otherwise, listing what it does have.
Two additions worth making at the same time, because they are the blocker `FOLLOWUPS.md` records
for the online-refresh feature and they are cheap here:

- `?meta=1` returning the envelope without `api[]`, so "is there something newer" costs bytes
  instead of megabytes.
- An `ETag` on the full response.

**Payload size is a real constraint.** The route currently does
`import * as gscApiT7 from "$lib/apiSource/t7_api_gsc.json"` — a static import, bundled and held in
memory. Eight files is ~7.5 MB of JSON; statically importing all of them would bloat the server
bundle and the cold start. Switch to reading from disk per request (adapter-node) or `await
import()`, and cache the parsed result per `(game, language)`.

**UI.** A game switcher in `LibrarySidebar`. `ApiLibrarian` already exposes `set gameId`, and
already short-circuits when `(gameId, languageId)` is unchanged, so this is mostly wiring plus a
navigation. The language tabs should offer CSC only for games that have it — `waw`, `bo1`, `bo3`.

**Render provenance honestly.** A game-level banner from the `provenance` block ("WaW's signatures
are inherited from Call of Duty 4 and are not verified for this game"), and a per-entry badge for
`aiGenerated` with the entry's `remarks` shown — the data already carries a full justification
string per reconstructed entry, and `ScrFunctionSchema` already models `remarks`.

**Two more libraries worth serving.** The site renders neither object fields nor Radiant keys today,
and the extension bundles five games' worth of both (`*_object_fields.json`, `*_radiant_keys.json`).
They are small, they are the thing people search for, and they need no new data.

### Phase 3 — the extension

`client/src/extension.ts` composes the URL; it already knows the game (`settings.game`, and the
server's authoritative answer arrives on `gscode/serverReady`). Use the latter:

```ts
page = `https://www.gscode.net/library/${activeGame.game}/${builtin.language}/${builtin.name.toLowerCase()}`;
```

`BuiltinAtHandler` needs no change — it deliberately returns a name and a language, not a URL,
"so the server should not need redeploying if that changes". That decision pays off here.

Optionally, once `?meta=1` and `ETag` exist, the proposed `gscode.apiUpdate.enabled` becomes
buildable per game.

### Phase 4 — new games' data

This is the "fuck knows" half, and it splits cleanly by how much is actually obtainable.

**A word on what a new game costs.** Data alone does nothing: `DataFilePrefix` lives on
`GameProfile`, and the thirteen unimplemented games are `Core(…)` entries with `DataFilePrefix =
null`. So each new game is three pieces of work, in order — **promote the core** (confirm the
dialect axes against ~15 real scripts, per `add-game-profile`), **get a corpus** (`GSCODE_CORPUS_<GAME>`,
to earn `Verified`), **then generate the library**. The library is the last step, not the first.

#### Tier A — done

`cod4`, `waw`, `mw2`, `bo1`, `bo3`. Nothing to acquire.

#### Tier B — names are obtainable, signatures are not

`xensik/gsc-tool` carries flat `{ id, "name" }` builtin tables per engine, at
`src/gsc/engine/<engine>_func.cpp` and `_meth.cpp`. Verified counts (free functions; methods are a
comparable second file):

| game | engine | funcs | notes |
|---|---|--:|---|
| MW3 (2011) | `iw5_pc` | 455 | |
| Ghosts | `iw6_pc` | 605 | |
| Advanced Warfare | `s1_pc` | 735 | |
| Infinite Warfare | `iw7` | 806 | |
| WWII | `s2` | 1,000 | IW6-derived; some names community-resolved |
| MW2019 | `iw8` | 1,065 | |
| MW2022 | `iw9` | 905 | 889 named, 16 still `_func_<hash>` |
| Vanguard | `s4` | 693 | |

**This is exactly the layer the pipeline already has.** A name-only list is the generator's fourth
precedence layer ("the bare wordfile name, so a function documented nowhere is still known to
exist"). A new reader beside `GenerateWordfileGameData` — call it `GenerateFuncTableGameData` —
producing a library with `HasCompleteBuiltinLibrary = false`, `HasReliableBuiltinSignatures =
false`, and `enrichFrom` pointed at a sibling in the same lineage for descriptions. MW2 is the
worked precedent for precisely this shape, including the reservation about what such a library may
and may not be used to claim.

Licensing: gsc-tool is **GPL-3.0**. The existing rule already covers it — read the tables from a
path given by an environment variable (`GSCODE_GSCTOOL`, the same posture as `GSCODE_COD4_DOCS`),
import the derived names, vendor nothing. A bare list of engine API names is a fact, not the tool's
code; but the tool's files must not enter the repo.

Suggested first target: **Ghosts** or **MW3**. Both are IW-line, so the dialect is close to MW2's
(already proven), and `enrichFrom = "mw2"`/`"cod4"` gives real descriptions for the shared names.

#### Tier C — hashed, no flat table

BO4 (`t8`), BOCW (`t9`), MW2023 (`jup`), BO6 (`t10`). Function identity is a hash; names are
recovered piecemeal by dictionary brute-force in `ate47/atian-cod-tools` rather than checked in as a
per-game array. gsc-tool marks T8/T9/T10/jup WIP and ships no func tables for them.

Recommendation: **do not start here.** A partial, hash-derived name list with no signatures and no
completeness claim is the weakest possible library, and every rule that could use it is already
gated off for exactly that reason. Revisit if ACTS ever publishes a stable per-game name table.

#### Tier D — nothing public and structured

BO2 (`t6`). No official tools ever shipped; gsc-tool has opcode and dvar-hash tables for T6 but no
GSC builtin function table. Community lists exist and are unverified.

#### On entity fields and Radiant keys for new games

No canonical source exists past the SDK era. For a Tier B game the realistic route is the same
empirical one already used for MW2's client libraries: sweep that game's decompiled script corpus
for `self.<field>` access patterns and mark everything `aiGenerated`. Worth doing only after the
function library, and only for a game whose corpus is configured.

## 4. Verification bar

Two invariants, both cheap, both catching a whole class:

1. **Site-side**: a test asserting every file in `site/src/lib/apiSource/` parses against
   `ScrLibrarySchema`. This is the permanent fix for §2.1 and for anything like it.
2. **Server-side**: `BundledDataTests` already asserts every file a profile promises actually ships;
   extend it to assert the envelope is present and `gameId` matches the profile's `Id`.

Plus the existing bar for any promoted core, unchanged: no crashes, lex/parse failures under 1%,
formatter round-trip clean over a 250-file sample, before `Verified = true`.

## 5. Sequencing and what each phase buys

| phase | work | buys |
|---|---|---|
| 0 | field-data writer: envelope, provenance, flag vocabulary | nothing visible; unblocks everything |
| 1 | build-time copy, delete the duplicate | drift class gone |
| 2 | site routes, API, switcher, provenance UI | **five games' libraries become browsable** |
| 3 | client URL composition | shift+F1 correct on all five |
| 4 | per-game acquisition, one at a time | a sixth game, then a seventh |

Phases 0–3 are the whole of the near-term value and touch no new data. That is the argument for
doing them before any acquisition work: the four pre-BO3 libraries are already better than anything
the site shows, and today literally nobody can see them.

## 6. Loose ends found while investigating

- **`GAME_PROFILES.md` function counts look stale.** It records WaW at 891 GSC / 154 CSC and BO1 at
  751 / 156; the files hold 1,060 / 188 and 1,377 / 320. Probably counted before a later enrichment
  pass. Worth confirming and correcting, since those numbers are cited as evidence.
- **Pre-BO3 object fields are one kind only.** `cod4/waw/mw2/bo1_object_fields.json` each hold a
  single `entity` bucket of ~108 fields (the wordfile's `/C2` list), against BO3's ten kinds and 635
  fields. Not wrong, but the site should not present them as equivalent.
- **`getLibrary`'s doc comment is wrong.** It says the route serves "requests made by the GSCode
  Language Server"; the server contains no HTTP client at all and never has. It describes the
  unbuilt `apiUpdate` feature.
- **`waw_clientkeys.txt` and `bo1_clientkeys.txt` do exist** in `sources/originals/` — worth noting
  against any external source that claims otherwise. CoD4 has none, consistent with it having no
  client scripts.

## 7. What shipped

The site now serves all five games. What was actually built, and where it differs from the plan
above:

**Phase 0 moved from the generator to the endpoint.** The plan was to add the envelope to the four
pre-BO3 artifacts in `tools/field-data`. That was not done, deliberately: regenerating rewrites files
hashed into `ServerBuildIdentity` and invalidates every workspace cache on every machine, which is a
large price for a change the site can absorb by itself. `/api/getLibrary` now completes the envelope
from the game registry instead. The artifacts are untouched, and the generator change remains
available later as a tidy-up rather than a prerequisite.

**Phase 1, as planned.** `npm run sync:api` copies the server's artifacts into
`site/src/lib/apiSource/`; `-- --check` asserts they are in step. Running it resolved the existing
drift in the two BO3 files.

**Phase 2, as planned, plus what the build turned up.** Routes are
`/library/<game>/<gsc|csc>/<function>`, with 301s from every pre-existing URL shape. `getLibrary`
serves any of the eight artifacts, accepts either `bo3` or `t7`, and gained `?meta=1` and an `ETag`.
Libraries load through `import.meta.glob`, so each is its own chunk rather than 7.5 MB in the server
bundle. The sidebar gained a game picker, and the language control now offers CSC only for the three
games that have client scripts.

Three things only surfaced once real data went through the schema:

- **`flags` is absent entirely on some entries** — 113 of WaW's, 12 of its CSC library's, 3 each in
  CoD4/MW2/BO1. It was a required array, so those libraries threw on parse. Now defaulted to `[]`.
- **`description` is absent on up to 127 entries** per library; already defaulted, so it survived.
- **`ApiLibrarian` cached on the payload's `gameId`**, which is the prefix (`t7`) and never equals
  the requested slug (`bo3`). Every read was a cache miss refetching 2.9 MB. Now keyed on the
  request.

**Provenance is rendered, not just carried.** Each page states what its library is — documented,
partial, or reconstructed — and an entry flagged `documented` on an inheriting game says
"documented elsewhere", naming the sibling, rather than claiming a page that game never had.

**Phase 3 landed too.** `gscode.openApiLibrary` now builds `/library/<game>/<language>[/<name>]`.
The game comes from the module-level `activeGame`, held from `gscode/serverReady` — the server's
answer, not `gscode.game`, because an unrecognised value in that setting resolves to Black Ops III
server-side and the setting can therefore name a game the session is not running. The status bar has
always used the server's answer for that reason; a URL is the same question. `BuiltinAtHandler` was
not touched: it returns a name and a language deliberately, so that how the site addresses its pages
never requires a server redeploy.

That exposed one case the client cannot answer: a `.csc` buffer open under Call of Duty 4 or Modern
Warfare 2, which have no client scripts. The client does not know which games do — that is
`HasClientScripts`, server knowledge — so the site answers instead, 301ing `<game>/csc` to the
game's one library and keeping the function segment. The same redirect fixes a hand-typed URL.

The language control is also hidden entirely on those two games rather than rendered with one
option, which read as a missing choice rather than an absent one.

**Still open:**

- **The parse invariant.** The proposal called for a test asserting every artifact parses against
  `ScrLibrarySchema` — exactly the class of bug the missing `flags` turned out to be. The site has no
  test runner, so adding one is its own decision; until then the failure mode is a 500 on that game's
  page rather than a red build.
- **Phase 4** entirely, and the object-field and Radiant-key libraries.
