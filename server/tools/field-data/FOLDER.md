# tools/field-data

All engine object-field source data, plus (from P7) the dev-time tool that converts it
into the runtime artifacts bundled in `GSCode.Workspace/Api/`. Nothing here is read from a
game install at runtime.

## sources/originals/

Verbatim copies from a game install, kept as provenance for the curated layer.
Re-imported only if a game update changes them.

- `ScriptObjectFields.xlsx` — from `%TA_TOOLS_PATH%\docs_modtools\`; 10 tabs
  (Weapons, CG DynEnt, CG Cent, Actor, Client, HudElem, Vehicle, Ent, PathNode,
  Sentient) mapping field name → engine type token (F_INT, F_FLOAT, F_STRING,
  F_LSTRING, F_VECTOR, F_WEAPON, F_ENTHANDLE, F_BYTE; 0 = untyped).
- `keys.txt` — from `%TA_TOOLS_PATH%\share\raw\radiant\`; 424 lines of map-entity KVP
  keys, format `[client] <type> <field> // comment`. The `client` prefix marks
  CSC-only keys; inline comments become hover docs.

### The pre-BO3 games (CoD4, WaW, BO1)

Each ships a mod-tools wordfile with the same `/L11 "CODSCRIPT"` layout, so one reader
serves all three (`GenerateWordfileGameData`).

- `cod4_wordfile.txt`, `waw_wordfile.txt`, `bo1_wordfile.txt` — the syntax-highlighting
  wordfile (`bin\wordfile.txt`). `/C7 "Script Commands"` → builtin function names,
  `/C2 "Common Entity Properties"` → entity `.fields`. The tool parses both.
- `cod4_keys.txt`, `waw_keys.txt`, `bo1_keys.txt` — each game's `raw\radiant\keys.txt`,
  through the shared radiant-keys parser, so their keys carry types.
- `waw_clientkeys.txt`, `bo1_clientkeys.txt` — `raw\radiant\clientkeys.txt`. The pre-BO3
  Treyarch games say "this key is client-side" by SPLITTING the data across two files,
  where BO3 keeps one and prefixes the line with `client`. Their `keys.txt` carries no
  prefix at all, so without the second file the distinction is lost entirely and the
  client-only keys are missing outright: 126 of BO1's, 11 of WaW's. CoD4 has no such file,
  and no client scripts either — the cross-check that this is a Treyarch convention.

Two things the wordfiles taught us, worth knowing before trusting one:

- **BO1's is not BO1's.** Its `/C7` is the same 755 functions as CoD4's, differing only in
  how `moveto` is written — the file was carried forward across CoD4, WaW and BO1 without
  ever being updated. WaW's is genuinely its own: 110 of its functions are absent from
  CoD4's.
- **A wordfile has no signatures.** It is a list of names, which is why a library built
  from one sets `HasCompleteBuiltinLibrary = false`: good enough to complete and hover
  from, not good enough to claim a name is NOT an engine function.

`cod4_stock_scripts.txt` (in `Api/`) is NOT generated by this tool — like the BO3 stock
list it is a one-off dump of the raw script tree, produced with:
`find . -name "*.gsc" | sed 's|^./||' | tr 'A-Z' 'a-z' | sort` from the CoD4 `raw\` root.

## sources/curated/

The EDITABLE source of truth — plain diffable JSON we control, correctable and
extensible beyond stock data. Field entry shape: `{ "name", "type", "readonly"? }`.

- `ai_fields.json`, `aitype_fields.json`, `entity_generic_fields.json`,
  `hudelem_fields.json`, `pathnode_fields.json`, `player_fields.json`,
  `sentient_fields.json`, `vehicle_fields.json`, `vn_fields.json` — per-entity field lists.
- `weapon_fields_simple.json` — weapon fields; every entry carries `"readonly": true`.
- `clientfield_enums.txt` — clientfield enum reference material.
- `cod4_ai_builtins.json` — reconstructed entries for CoD4 functions no documentation
  covers. Every one carries the `aiGenerated` flag and a `remarks` line naming its
  provenance: thirteen carried over from the Black Ops III library, where the same function
  is documented, and six inferred from call sites alone. Kept here so a regeneration cannot
  drop them, and flagged so a reconstruction is never mistaken for documentation.

The object-field sweep matches `*_fields*.json` ONLY. A plain `*.json` glob turned
`cod4_ai_builtins.json` into a bogus `cod4_ai_builtins` entity kind; narrowing it to
`*_fields.json` then silently dropped `weapon_fields_simple.json`. Both showed up as a diff
in the generated artifact, which is the argument for keeping those committed.

## The tool

`GSCode.FieldData.csproj` + `Program.cs` — a dev-time console generator, deliberately kept
OUT of `GSCode.slnx` so it is never a server build or runtime dependency. Run it by hand
with `dotnet run` from this folder after editing the curated sources.

- Merges every `sources/curated/*_fields*.json` into `GSCode.Workspace/Api/t7_object_fields.json`
  (a `{ entityKind: [ {name, type, readOnly} ] }` document, sorted for clean diffs). Entity
  kind is the file stem minus `_fields`/`_simple` (`entity_generic` → `entity`).
- Parses each game's radiant keys into `<prefix>_radiant_keys.json`
  (`[ {name, type, side, comment} ]`, sorted). Where a game also has a `clientkeys.txt`, a
  key found only there is recorded as client-side.
- Generates each pre-BO3 game's `<prefix>_api_gsc.json` and `<prefix>_object_fields.json`
  from its wordfile.
- The `import` step (xlsx → curated) is manual; the curated JSON is the source of truth.

### How an API entry is chosen

Four sources, highest precedence first. Each only fills a gap the one above left:

1. **A documentation page** for that function (CoD4 only — see `GSCODE_COD4_DOCS`).
2. **A curated reconstruction** from `sources/curated/<prefix>_ai_builtins.json`.
3. **A sibling game's entry** of the same name, for games in one engine lineage
   (`enrichFrom`). This is how all 751 of BO1's names arrive with descriptions and
   parameters rather than bare: they are the same functions CoD4 documents.
4. **The bare wordfile name**, so a function documented nowhere is still known to exist.

The run prints the split, e.g.
`cod4 api functions: 819 (792 documented, 19 reconstructed, 0 inherited, 8 name-only)`.

### Environment variables

- `GSCODE_COD4_DOCS` — the CoD4 per-function documentation pages. **Not vendored**: they are
  a third party's, so the tool reads them from wherever they live, exactly as the corpus
  tests locate game scripts. Unset means the wordfile names alone, which is the state the
  artifact was already in — a regeneration without the docs never silently loses detail, it
  just stops gaining it.

The corpus environment variables (`TA_TOOLS_PATH`, `GSCODE_CORPUS_<GAME>`) belong to the
tests; see `tests/FOLDER.md`.

### Output conventions

Artifacts are written **ASCII-only**, with the relaxed JSON encoder. The default encoder
escapes `<`, `>`, `&` and `'` as unicode escapes, which in documentation text full of
`<target>` placeholders produced 1,470 of them in a single file; typographic characters
(smart quotes, dashes) are folded to their ASCII equivalents rather than escaped. Newlines
are pinned so a regeneration on Windows does not rewrite every artifact as CRLF.
